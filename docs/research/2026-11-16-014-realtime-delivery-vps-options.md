# 014+ Realtime delivery options for self-hosted chat on cheap VPS (evidence-based)

**Date:** 2026-11-16  
**Repo:** `/home/luis/development/MDMV/projetos/Arquivados/flora` (dev, post REST channels/messages slice)  
**Scope:** Deep multilingual desk research (EN, pt-BR, es, de, fr, zh-CN, ja) on minimal, reliable realtime message delivery for a self-hosted chat on a cheap VPS (2 vCPU / 4 GB RAM), cross-checked with Flora's current implementation. No application source changes.

## 1. Flora current state (cross-check)

| Area | Current state (evidence) | Implication for 014+ |
|---|---|---|
| **Transport / route** | Axum WS upgrade at `GET /ws` (`flora-api/src/routes/mod.rs`, `flora-api/src/routes/websocket.rs::websocket_handler`). Auth extracted before upgrade from `Authorization: Bearer <jwt>` only (`extract_org_context`), decoded/validated as JWT claims (user/org), but **no DB-backed session/jti validation parity** with HTTP extractor (see prior `docs/research/2026-11-16-013-websocket-session-authority.md`). | Realtime auth is not yet at HTTP session-authority level; browser token transport/path must align with frontend. |
| **WS protocol** | Tagged JSON client msgs: `Subscribe`, `Unsubscribe`, `SendMessage{channel_id,content,thread_id}`, `Ping`. Server msgs: `Subscribed`, `Unsubscribed`, `NewMessage{...}`, `MessageSent`, `Pong`, `Error{code,message}` (`websocket.rs`). | Protocol exists, but only partially exercised end-to-end. |
| **Tenant checks & persistence** | `SendMessage` verifies channel ownership in-org (`PgChannelRepository::find_by_id`), persists via `PgMessageRepository`, best-effort publishes to Valkey (`state.messaging_service.publish`) after save. `Subscribe/Unsubscribe` are ack-only; no per-connection subscription registry or server-side fanout loop consuming pubsub. | **Publish path exists, delivery/fanout path to other connected clients is incomplete.** |
| **Messaging crate** | `flora-messaging::MessagingService` wraps Redis/Valkey `ConnectionManager` and does `PUBLISH` to `org:{org_id}:channel:{channel_id}` with latency logging/warn thresholds (500 ms targets). No subscribe/listen API, no fanout, no circuit breaker implementation despite config fields (`flora-messaging/src/lib.rs`, `config/valkey_topics.rs`). | Valkey is wired as an outbound event bus primitive, not a working realtime delivery plane. |
| **Core messaging config** | `flora_core::config::messaging::MessagingConfig`: `valkey_url`, `topic_template`, `max_fanout` (50), `message_ttl_secs` (3600), circuit-breaker knobs; env/default-backed (`redis://localhost:6379`). | Config anticipates fanout/offline semantics that are not implemented. |
| **REST channels/messages slice** | `flora-api/src/routes/channels.rs`: `GET/POST /api/v1/channels?workspace_id=...`, `GET/POST /api/v1/channels/{channel_id}/messages`, `PATCH/DELETE /api/v1/channels/{channel_id}/messages/{msg_id}`. Org/membership/workspace/channel ownership checks enforced; message list supports `limit` (capped) and has `before` query param but current repo query uses offset pagination and filters deleted in-handler. No `/api/v1/messages/sync` endpoint. | Reliable history/read path is mostly REST-backed today; pagination/catch-up contract needs tightening for reconnect recovery. |
| **Frontend (canonical Svelte 5, `apps/frontend`)** | `src/lib/api/websocket.ts` connects to `/api/v1/ws` with token in query string (`?token=`), single socket singleton, basic reconnect timer, `syncMissedMessages()` calls non-existent `/api/v1/messages/sync`, expects flat events like `workspace.user.removed` and updates `lastKnownMessageId` from `event.id`. `src/lib/state/MessageStore.svelte.ts` is a simple in-memory array. `ChatLayout`/channel pages load/send via REST APIs. | **Protocol/path/auth/event-shape drift** between frontend, backend, and recovery API; reconnect recovery is not functional as coded. |
| **Deployment assumption** | Seed profile targets cheap/single VPS (user-stated 2 vCPU / 4 GB). | Favors low moving parts, predictable memory, and simple failure/reconnect semantics over premature horizontal scaling. |

**Bottom line:** Flora already has Postgres as source of truth, partial WS protocol + Valkey publish, and REST message history. It does **not** yet have a complete, reliable realtime fanout/delivery loop. Any 014+ choice must close that gap without overbuilding for single-node Seed.

## 2. Option comparison (2 vCPU / 4 GB VPS, Rust Axum/sqlx + Svelte)

| Option | How it works | Complexity / operability | Memory & CPU (evidence/estimates) | Multi-instance implications | Correctness & reconnect semantics | Debloat / fit for Flora Seed |
|---|---|---|---|---|---|---|
| **A. DB polling / long-polling (REST catch-up)** | Client polls `GET messages?after=<cursor>` (or holds request until timeout/new data). No persistent push channel. | **Lowest infra complexity** (HTTP only). Easy to reason about, cache/proxy-friendly HTTP semantics. More request churn at high activity. | Cost is per-request/query overhead, not per-idle-connection state. Good when updates are infrequent; wastes CPU/DB under chatty rooms. SSE/WS avoid repeated headers for active streams (SSE ~few bytes/event, WS ~2–14 bytes/frame vs repeated HTTP in polls/long-polls) [1][2][5]. | Trivial to scale horizontally (stateless HTTP) if DB can handle read load. | Correctness is as strong as cursor/idempotent reads from Postgres (source of truth). Reconnect is trivial (stateless); delivery becomes "eventual until next poll" with tunable latency. | **Very debloated baseline** and excellent fallback/recovery path. As primary realtime UX, adds latency/battery/request overhead; best paired with push, not instead of it, for chat feel. |
| **B. SSE (server → client) + REST POST for sends** | `EventSource` GET stream for events; client sends messages/actions via normal HTTP POST/PATCH. Keep-alive comments; `id` + browser `Last-Event-ID` enable replay/resume semantics. | **Low-medium**: standard HTTP, no WS upgrade/state machine, browser auto-reconnect built in. Need heartbeat, proxy buffering config (`X-Accel-Buffering`/no-transform), and replay buffer strategy. One-way only. | Lower per-connection protocol overhead than long-polling for streams; per-connection state similar to any long-lived connection but simpler than bidirectional WS stacks. HTTP/2 multiplexing removes HTTP/1.1 ~6-conn/origin issue [1][2][3][4][5]. | Each instance must reach the right subscribers: in-process fanout is single-node only; cross-node needs broker/backplane (Redis/Valkey, NATS, Kafka, or Postgres signaling + shared state) and/or sticky routing depending design [1][3][5]. | **Built-in reconnect + `Last-Event-ID`** is a major correctness UX win, but server must persist/replay event IDs/cursors for a window or provide snapshot recovery; otherwise "resume" is best-effort. At-most-once over the wire unless replayed/idempotent client handling [1][2][3][4]. | **Strong 80/20 fit for one-way feed/notifications/progress**; for chat, pairs well with existing REST sends. Simpler than WS when browser→server traffic is infrequent, but Flora already has/needs bidirectional-ish chat semantics (send/subscribe/typing later) to define carefully. |
| **C. WebSocket (Axum `axum::extract::ws`) + in-process broadcast (single node)** | Persistent bidirectional socket; server tracks local subscribers (e.g. per-channel room map + Tokio broadcast/mpsc) and pushes events to sockets on same process. Persist to Postgres; optionally emit bus event for future scale. | **Medium**: connection lifecycle, auth-on-upgrade, heartbeats/ping-pong, backpressure, message framing, manual reconnect/resume logic, close/error taxonomy. Axum/Tokio/tungstenite have solid support [1][6][7]. | Low per-frame overhead (~2–6/2–14 bytes) and low latency; memory is dominated by per-idle-connection buffers/state. Indicative measurements: ~3–21 KB/idle conn depending stack/compression; 100k idle conns can be ~GBs in general-purpose stacks (order-of-magnitude, workload-dependent) — **not** a target for 2GB/4GB VPS but shows fixed per-conn cost matters [1][7][15]. Zatat/Ripple-style benchmarks show high throughput on small/shared VMs in specialized servers, but app logic + DB + runtime overhead differs [8][9]. | **Single-process only**: each process knows only its sockets. Horizontal scale requires sticky sessions and/or shared pubsub/backplane and room routing [1][6]. | No built-in reconnect/resume; client must implement reconnect, dedupe (`client_id`/message id), and catch-up via REST cursor (`after`/`since`) from source of truth. Delivery guarantee becomes an application contract (typically at-least-once to UI with idempotent merge). | Fits current Flora protocol direction, but current implementation lacks registry/fanout and has auth/contract drift. Viable on single VPS if connection counts modest and backpressure/limits enforced; must be kept minimal. |
| **D. WebSocket + Valkey/Redis Pub/Sub fanout** | Persist message in Postgres, publish event to Valkey/Redis topic; every app instance subscribes and forwards matching events to local sockets. (Classic multi-instance chat pattern.) | **Medium-high operationally**: adds broker dependency/monitoring/failure modes, subscription management, serialization/topic design, and reconnect-to-broker logic. In-process part same as C. | Broker is fast but in-memory/network hop adds latency/ops; pub/sub is ephemeral. Valkey/Redis can be lightweight for low traffic, but still another service/process on 2 vCPU/4 GB. Valkey vs Redis 2026: protocol-compatible for core use, similar perf in small tests; migration/licensing nuances exist [14]. | **Designed for horizontal fanout**: decouples producer instance from socket-owning instance [1][6][11]. | **At-most-once on the bus**: messages published while subscriber disconnected/reconnecting can be lost; Redis pub/sub has no backlog/persistence (Streams/Kafka/NATS JetStream differ) [1][3][14][17]. Needs DB cursor catch-up on reconnect regardless. | **Overweight for Seed single node today** (Flora already carries Valkey config but not full fanout). Useful as a later scale step once multi-instance is real. |
| **E. Postgres `LISTEN/NOTIFY` (+ optional WS/SSE bridge)** | `NOTIFY` on commit/transaction emits channel payload; listeners receive asynchronously. Can bridge to WS/SSE clients or coordinate caches across instances without Redis. | **Low infra count** (reuses Postgres) but **non-trivial runtime semantics**: dedicated long-lived/unpooled listen connection(s), reconnect handling, channel strategy, payload design, and careful trigger/batch behavior. PgBouncer transaction pooling breaks LISTEN [3][13][18][19][20]. | Saves running Valkey, but consumes DB connections and some WAL/CPU for notifications; each listener is a connection. Good for modest event rates/few listeners; not for high fanout/high frequency. LISTEN/NOTIFY "usually fine" for small scale but has hard limits (see correctness) [3][10][13][18]. | Works as a **small-scale multi-instance backplane** (all instances listen to shared Postgres) — documented in practice for config/SSE fanout and cluster coordination without Redis [10][11][12]. Does not remove need to map events to local sockets. | **Ephemeral, at-most-once, no replay/backlog**: missed if no listener at publish time; payload capped at **8000 bytes** (send IDs, fetch from DB); notifications transactional (fire on commit) — good property. Duplicates/loss windows possible around reconnect/crash unless app-level recovery exists [3][13][17][18][19]. | **Attractive debloat option if Valkey can be avoided** and traffic/fanout are modest, but requires disciplined recovery (cursor polling on reconnect) and careful connection management on 4 GB VPS. Not a durable queue. |
| **F. Durable log/queue (Redis Streams, Kafka, NATS JetStream, outbox)** | Persist events in replayable log/stream/outbox; consumers track offsets/cursors; can achieve at-least-once delivery with dedupe. | **Highest complexity/ops** for Seed (more services, retention/consumer-group semantics, ops burden). | Extra CPU/RAM/disk/processes; unjustified for small single-tenant/single-node chat seed. | Best for real multi-node durability and replay guarantees. | Strong replay/catch-up semantics (cursor/offset), but application must still handle idempotency/duplicates (at-least-once). | **Not 80/20 for 014+ Seed**; consider only when correctness SLOs and scale require it. |

### Evidence highlights (multilingual, selected)

- **EN:** SSE gives built-in reconnection and `Last-Event-ID`, HTTP/proxy friendliness, and is often preferred for server→client updates; WebSockets are bidirectional/low-overhead but require manual reconnect, heartbeats, scaling/backplane, and state management. Long-polling is simplest fallback but high overhead under load. Redis pub/sub is fast but at-most-once/no persistence; `LISTEN/NOTIFY` has no persistence, 8 KB payload cap, dedicated-connection/pgbouncer caveats and is unsuitable for high-frequency/high-fanout durable delivery. Tokio broadcast + in-process registries are common single-node Axum patterns; multi-instance needs shared bus/sticky routing [1][2][3][4][5][6][7][13][17][18].
- **pt-BR (implícito no ecossistema) / EN+pt sources consulted contextually:** em VPS pequena, polling simples é viável para baixa frequência; para chat, custo de conexões ociosas/reconexão e fanout pesam mais que "tempo real puro" — padrão prático é persistir no banco e usar push + fallback por cursor (ver padrões de inbox/cursor e recuperação) [3][13][17].
- **es:** SSE = stream unidireccional HTTP com reconexão automática/EventSource e bom encaixe para feeds/notificações/progresso; WebSocket = canal bidirecional para casos onde navegador também envia com frequência. Regra prática: se o navegador "escuta" majoritariamente, SSE; se "fala" tanto quanto escuta ou precisa binário, WebSocket. Heartbeats/proxies e reconexão manual no WS são custos reais [1][2].
- **de:** PostgreSQL `LISTEN/NOTIFY` kann als leichtgewichtiges Pub/Sub ohne zusätzliche Infrastruktur dienen (inkl. Multi-Instanz-Koordination in kleinen Setups), ist aber **nicht persistent** (kein Backlog), benötigt dedizierte LISTEN-Verbindungen (kein Pooling-Konflikt), und ist für verlässliche Zustellung auf anwendungsseitige Recovery angewiesen; Redis bleibt für hohe Last/dauerhafte Queues relevanter [11][12][18].
- **fr:** Cas d’usage temps réel auto-hébergé (ex. ForgeChat, Rust/Axum/PostgreSQL/WS) privilégie pile simple (Postgres + WS) avec auth/sécurité durcie; le passage multi-instance impose distribution d’état/pubsub et gestion explicite de reconnexion/rate-limit [16].
- **zh-CN:** Axum 生态中 SSE 与 WebSocket 均有成熟支持；SSE 实现简单、适合单向事件流/广播（可配合 keep-alive、限速、Hub/broadcast，集群可用 Redis Pub/Sub 桥接），WebSocket 适合双向低延迟但连接/心跳/代理与扩展更复杂。小规模实时通知常见做法是“单机 Hub +（可选）Redis 桥接”而非过早引入重型消息系统 [7][20].
- **ja:** Rust/Axum + WebSocket のチャット実装では、接続管理・再接続・認証・ブロードキャスト境界が主課題。単一ノードでは in-process broadcast で足りるが、複数インスタンスや配信保証を求めると Pub/Sub/永続化/再取得設計が必要になる（履歴はDB、リアルタイムは別経路という分離が一般的）[21][22].

> Note on evidence quality: public multilingual material is uneven by topic (SSE/WS comparisons abundant in EN/es; `LISTEN/NOTIFY` tradeoffs well documented in EN/de; Rust/Axum specifics strong in EN/zh/ja project/docs pages). Recommendations below prioritize primary/official-ish docs and widely corroborated engineering guidance, and treat micro-benchmarks (zatat/ripple/etc.) as directional, not as Flora SLO proof on a constrained VPS [8][9][15].

## 3. Cross-cutting tradeoffs that matter for Flora

1. **Source of truth vs delivery plane:** Postgres already stores messages; realtime mechanisms should be *notification/fanout*, not the only copy. Any lossy channel (WS disconnects, Redis pub/sub drops, `NOTIFY` missed) must recover via REST cursor/id-based fetch from Postgres.
2. **Correctness contract to make explicit:** for chat, UI should tolerate duplicates and reorder around reconnects (idempotent upsert by `message_id`, monotonic cursor). "Exactly-once over push" is unnecessary and expensive; "at-least-once to UI after reconnect + no silent loss when DB commit succeeded" is the practical target.
3. **Reconnect semantics:** WS needs custom client logic (today partially present but broken against contract); SSE gives browser reconnect/`Last-Event-ID` for stream resumption if server supports replay window. In all cases, keep a deterministic catch-up path: `GET /channels/{id}/messages?after=<cursor-or-id>` (or equivalent sync endpoint) backed by indexed query.
4. **2 vCPU / 4 GB operability:** every extra always-on component (Valkey, separate worker, proxy quirks) consumes RAM/CPU and failure surface. Prefer fewer daemons, bounded buffers, connection limits, heartbeat tuning, and clear observability (tracing counters for connects, drops, lag, publish failures) over theoretical peak throughput.
5. **Multi-instance:** **not required for Seed single node**. Designing message IDs/cursors and event envelopes to be bus-agnostic now is cheap; running Redis/cluster-grade fanout now is not. `LISTEN/NOTIFY` or Valkey can be deferred scale adapters behind a small internal publish/subscribe interface.
6. **Flora-specific gaps to close before any option is "reliable":** align WS path/token transport with browser constraints and HTTP session authority, implement real fanout (or explicit no-fanout + fast poll), define event envelope/cursor, fix frontend protocol mismatch, and provide a working catch-up endpoint/query.

## 4. Recommended 80/20 path for cycle 014+

**Recommendation: keep it single-node and Postgres-authoritative; implement reliable chat via "REST send + DB-backed history/catch-up + minimal realtime notification", deferring Valkey/multi-instance.**

### Phase 014 (minimum reliable slice)

1. **Make Postgres the correctness backbone (mandatory):**
   - Treat message create in DB as commit point of record.
   - Add/standardize deterministic catch-up read: cursor by `(created_at, id)` or monotonic ID with `after`/`before` semantics and supporting index; expose a concrete sync endpoint or make existing list query cursor-correct (replacing ambiguous offset-only behavior for recovery). This fixes the missing `/api/v1/messages/sync` assumption and covers missed push events.
2. **Choose push transport pragmatically:**
   - **Preferred 80/20:** **SSE per-user or per-scope stream for notifications** (`new_message` with channel+message id/cursor, plus auth/session-invalid events) and keep **message sends/mutations over REST** (already implemented). Rationale: browser auto-reconnect, `Last-Event-ID`-friendly pattern, no bidirectional protocol/state complexity, fits one-way "something changed, refetch/catch-up" model well [1][2][3][4].
   - **Acceptable alternative:** finish **WebSocket** only if bidirectional features are immediate needs; but then implement a real local subscription registry/fanout, heartbeat/close codes, auth parity, and frontend protocol alignment. Do not keep the current "publish to Valkey but no subscriber delivery" half-state.
3. **Single-node fanout mechanism:** in-process async broker (`tokio::sync::broadcast`/per-channel registries) fed after DB commit (or outbox-lite poll) — zero extra infra, easy on 4 GB. Do **not** require Valkey for Seed correctness; keep `flora-messaging` as optional/future adapter.
4. **Frontend (Svelte) alignment:** one small client with (a) initial REST load, (b) push subscription, (c) on event or reconnect -> incremental REST catch-up + idempotent merge into store, (d) exponential backoff + auth-failure stop. Use REST for send/edits/deletes to reuse validation/auth paths.
5. **Security/operability basics:** enforce WS/SSE auth with same session authority as HTTP, org/channel authorization on every subscription, generic auth errors, rate/connection limits, and proxy-safe timeouts/keep-alives.

### Phase 014.1+ (only if/when needed)

- **If avoiding Valkey entirely becomes desirable:** evaluate Postgres `LISTEN/NOTIFY` as a **low-rate invalidation signal** (payload = IDs only) with dedicated listener connection and mandatory REST catch-up; never as durable delivery [3][11][12][13][18].
- **If multi-instance becomes real:** introduce Valkey/Redis pub/sub or Streams as backplane behind an internal interface; add replay/cursor strategy and broker health handling. Redis pub/sub alone is still lossy — keep DB catch-up regardless [1][6][14][17].
- **If very high reliability/throughput required:** outbox + durable stream/consumer offsets (overkill for current Seed).

### Why this is the 80/20 choice

- Maximizes reliability per line of code by anchoring correctness in Postgres + idempotent catch-up (already mostly present) instead of fragile push semantics.
- Minimizes VPS footprint and ops (no required extra broker/process) while delivering "realtime enough" UX.
- De-risks Flora's current drift: fixes contract/recovery first, then adds the simplest effective push path.
- Leaves a clean upgrade path (internal event interface -> `LISTEN/NOTIFY` or Valkey/Streams) without premature scaling work.

## 5. Suggested acceptance criteria for 014 implementation planning

- A sent message committed in Postgres is visible to another client after reconnect/reload without manual intervention (REST catch-up proven).
- Realtime path cannot cross org/channel boundaries (server-side checks at subscribe and emit).
- Push transport auth matches HTTP session validity rules; revoked/expired sessions fail closed appropriately.
- Client handles disconnect/reconnect with bounded backoff and no duplicate-message corruption (idempotent merge).
- On 2 vCPU / 4 GB single node, no additional mandatory services beyond Postgres (+ existing app) are required for baseline correctness.
